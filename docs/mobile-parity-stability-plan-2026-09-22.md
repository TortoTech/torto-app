## P0：先解决 PDF 与翻译卡死

### 诊断基础

1. 保存安装包对应的构建标识；寻找匹配 build 7015 的符号再还原现有栈。下一次构建保留匹配的符号和源码版本，避免拿新构建符号解旧地址。
2. 新增异步轮转诊断文件，例如每份 1 MiB、保留 3 份；记录操作 ID、匿名书籍 ID、格式、章节/页、阶段开始/结束、耗时、generation、缓存字节数及生命周期。不得记录正文、译文、API key 或完整网络请求。
3. 覆盖 PDF open/interpret/render、翻译 request/validate/compose/reflow、图片解码与分页；补充 Flutter/异步异常处理、长帧与事件循环延迟，避免每帧刷盘。
4. Android 原生入口读取本应用历史退出信息，尽力保存可访问的 ANR trace；设置页提供导出诊断。Dart 心跳只能辅助发现延迟，不能独自抓取自己已经卡住的执行栈。

### PDF 路径

证据：`lib/core/formats/pdf/pdf_book_source.dart` 的 `openPdf` 虽声明 async，`PdfDocument.open`、元数据和目录读取仍同步执行；`pageText` 同步抽取。`pdf_rasterizer.dart` 直接进入纯 Dart PDF renderer，没有独立工作队列。需要实际 profile 判断其中哪一阶段是热点。

- 用单独、长期存活的 worker 管理文档解析、内容流解释和文字抽取；输入只传路径/字节和页号，避免每页重新解析整份文档或复制整个对象图。
- 先验证 PDF 库可输出可传输的绘制指令/数据。`dart:ui` 绘制、Picture/Image 对象不能简单整体搬入普通 isolate；界面侧仅保留必要的 Canvas 提交，并对可拆分工作分片。
- 如果现有库无法拆开解释和 Canvas 回放，再评估后台原生 PDF 渲染适配器；这是备选技术验证，不在本轮直接换引擎。
- 首屏优先，预读最多相邻页且串行；支持取消及文档 generation。复杂页设置工作量上限，不能依赖同一被阻塞 isolate 上的 Future.timeout 终止同步计算。
- 页面图像及底层解码缓存按字节预算统一核算，避免只限制图片边长。处理内存压力时清预读缓存。

### 普通电子书翻译路径

证据：`reader_controller.dart` 已有请求代次、250ms 合并、可见范围翻译和过期结果检查。但 `_applyTranslationUpdates` 每次有效批次仍调用整章 `_layoutSection`；`paginateAsync` 只在块间让出执行权，单个长段落/表格可以超出预算。后续 EPUB `parseSection` 的 XHTML/CSS 解析是同步工作，首次后台开书并不覆盖所有后续调用。

- 先分离测量“请求等待”和“验证/合成/重排 CPU”，不把异步网络直接当卡死根因。
- 每章节最多一个重排任务；新结果合并到最新 revision。任务内部检查取消/代次，而非仅在整章完成后丢弃结果；关闭翻译、退后台、退出阅读均释放旧任务。
- 分页暂停与取消分开，防止已销毁 reader 继续停在 `shouldPause` 的等待循环中。
- IR 解析、翻译校验和纯数据转换放到 worker；Paragraph shaping 留在 UI 所需线程。长段落的断行优化设置可中断的计算预算及保守降级，不截断正文。
- 第一阶段保留整章分页语义并改善调度；第二阶段再按脏段落复用 shaping，并从受影响锚点向后重排。不能直接只改当前页而破坏进度、选区、脚注映射。
- `_decodeSectionImages` 当前整章 `Future.wait`，改为小并发队列、去重及字节预算。普通翻译无需重复解码未变图片。

### P2 的移动端边界

- 默认关闭；选择独立识别模型，缺失配置时暂停，不偷偷替换模型。
- 保持桌面核心约束：模型仅输出现有 source ID 与角色；本地拒绝越界、重叠、不连续关系，不改写原文。
- 管线采用原文识别、翻译后组合，再进入排版；与翻译共享单一重排调度入口，禁止两个任务相互刷新整章。
- 当前章优先、单请求并发；退后台/离开 reader 取消，首版不做激进下一章预取。
- 保留内容+模型+prompt/schema 指纹缓存、空结果缓存、失败回退；未完成窗口不写作完整成功。
- 重排按源锚点恢复阅读位置，选区或翻页期间延迟安装结果；原版 PDF 排除。
- 数字标题保留候选过滤和章节二次审核，避免把页码识别成标题。不增加 TOC 边界。
- 首版缓存留本机，跨端同步另设计版本协议，不能把桌面私有缓存格式直接当同步协议。

## 实施与验收顺序

1. 诊断及复现：选取用户实际出问题的 PDF/EPUB（具体书名尚未提供），用 profile 测热点、release 验证响应；分别记录关闭/开启翻译基线。已有日志足以确认 ANR，尚不足以确认具体函数。
2. P0：按热点先修 PDF 或翻译路径，再实现取消、资源预算与持久日志。目标：两个场景各连续执行至少 20 次开关/翻页/进出后台无 ANR；取消后任务不继续安装结果，内存热身后不随循环持续上涨。
3. 性能验收记录首个可读帧、触摸响应 p95、最大 UI 连续占用、内存峰值。建议触摸反馈 p95 <100ms，普通可拆分计算片段 4–8ms；目标需由实机样本确认，不能把整章耗时误当连续冻结时间。
4. P1 分小批移植：先字号/图注/引用，再内容恢复。复用桌面语义测试样本，比较文本、锚点、链接、图片与双语定位，不要求两种渲染器像素完全一致。
5. P2 独立交付：使用固定模型响应做确定性验证；涉及真实书籍和付费模型的线上测试单独安排。回归离线、超时、切书、快速开关翻译和 AI 排版同时工作的情况。

本轮没有运行产品测试：未实现代码修复；这里的验收项是后续实施标准，不是已通过的测试结论。
